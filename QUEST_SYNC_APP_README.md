# Discord Times: перенос будущих квестов и добавленных объектов из DTm в SAV

## Запуск

Распакуйте **содержимое папки приложения непосредственно в корневую папку установленной Discord Times** (рядом с `Rus_Units.ini`) и откройте `run_quest_sync_gui.bat`. Если запуск через BAT недоступен:

```text
python dtm_to_sav_gui.py
```

При запуске приложение обязательно загружает игровые данные из этой же папки:

- `Rus_Units.ini`;
- `Rus_Artefacts.ini`;
- `Rus_Spells.ini`;
- `_Global.ini`;
- `Graphics\Objects\Objects.ugs`.

Если хотя бы один файл отсутствует или не разбирается, основное окно не открывается и показывается ошибка о том, что приложение нужно запускать из папки с игрой. Поиск этих файлов возле выбранной DTm/SAV не выполняется.

Если параметры юнитов, артефактов, заклинаний или `CostRecruitDiv` отличаются от встроенного профиля, приложение показывает **предупреждение**, но не блокирует сохранение. В расчётах используются именно текущие игровые файлы. Для изменённых параметров native-тестирование не гарантируется, поэтому такие derived-значения считаются экспериментальными и вычисляются формулами вместо использования несовместимого exact-профиля.

Файлы программы должны оставаться в одной папке:

- `dtm_to_sav_gui.py` — графический интерфейс;
- `dtm_sav_quest_sync.py` — основная синхронизация карты и SAV;
- `army_runtime.py` — синхронизация runtime-состояния армий и юнитов;
- `building_runtime.py` — structural/runtime-синхронизация строений, гарнизонов, казарм, рынков и святилищ;
- `army_catalog.json` — встроенный проверенный эталон для сравнения с текущими игровыми INI; рабочие характеристики при запуске берутся из файлов игры;
- `army_native_profiles.json` — нативно подтверждённые runtime-профили (`v1/v2`, base/modified strength, class) для наблюдавшихся Unit+Level и spell/artifact-комбинаций; выплата теперь вычисляется точной формулой и в профилях не хранится;
- `army_profile_miner.py` — извлечение и безопасное слияние новых нативных профилей из контрольных пар SAV/DTm;
- `tests/test_army_runtime.py` — формальный regression/property/fuzz-корпус армейского runtime;
- `tests/test_building_runtime.py` — regression-корпус строений и attached-garrison runtime;
- `tests/test_quest_sync_layout.py` — проверки layout/cell-table профилей;
- `tests/test_game_resources.py` — startup-загрузка игровых INI/UGS, сравнение с профилем и разрешённый fallback для модифицированных данных;
- `sav_tool.py` — чтение и запись контейнера SAV;
- `run_quest_sync_gui.bat` — запуск в Windows.

## Какие файлы выбрать

1. **Исходное сохранение SAV** — файл с игровым прогрессом.
2. **Оригинальная карта DTm** — неизменённая карта, на которой создано сохранение.
3. **Изменённая карта DTm** — версия с будущими событиями, текстами, новыми строениями, фонарями и/или декорациями.
4. **Новое сохранение SAV** — отдельный выходной файл.

При нажатии **«Обзор…»** приложение сначала ищет стандартные папки рядом с собой:

- для исходного и нового SAV — `Saves`;
- для оригинальной и изменённой карты — `Maps\_Rus`; также поддерживается вариант `Maps_Rus`.

В собранном EXE поиск выполняется относительно папки, где находится сам EXE. Если нужной папки нет, используется каталог уже выбранного файла либо стандартный каталог диалога Windows.

Сначала нажмите **«Анализировать»**. В таблице:

- зелёные события будут импортированы;
- красные уже затронуты сохранением и останутся без изменений;
- серые не отличаются в новой DTm и не требуют переноса.

В колонке **«Что изменено»** выводится краткая сводка правок события. При выборе
строки под таблицей показываются подробности: точные диапазоны изменённых байт
171-байтовой записи (`смещение: было → стало`) и изменения каждой из трёх
текстовых строк. Для уже затронутых событий отдельно показываются отличия
текущего SAV от оригинальной DTm, чтобы правки карты не смешивались с игровым
прогрессом. Различия только в представлении переносов строк (`CRLF`/`LF`/`CR`)
не считаются изменением; завершающие пустые строки также игнорируются. Внутренние
переносы строк остаются значимыми.

После проверки нажмите **«Создать новый SAV»**.

## Как определяется будущий квест

Для каждого события приложение сравнивает три записи:

- исходную запись из оригинальной DTm;
- текущую запись из SAV;
- новую запись из изменённой DTm.

Если запись в SAV уже отличается от оригинальной карты, событие считается начатым, выполненным либо изменённым движком. Оно полностью сохраняется. Если запись ещё совпадает с оригиналом, а в изменённой DTm была содержательная правка бинарной записи или текста, событие импортируется. Текстовые поля, в которых редактор изменил только формат переносов строк или удалил завершающие пустые строки, не перезаписываются в SAV.

Новые события также можно добавлять в конец списка. Их 171-байтовые записи и связанные текстовые тройки добавляются без изменения динамического прогресса SAV.

Такой критерий намеренно консервативен: сомнительное событие лучше сохранить, чем случайно сбросить прогресс.

## Синхронизация строений

Для `MapLDV V.4` поддерживаются **добавление, изменение, удаление, вставка и перестановка** 358-байтовых `BuildingData`. Строения выравниваются по тем же консервативным принципам, что и армии: неизменённые exact-survivors сохраняют свой runtime-прогресс, а структурные изменения приводят к перенумерации зависимых Building ID.

При изменении существующего строения используется трёхсторонний merge `оригинальная DTm / текущий SAV / изменённая DTm`. Благодаря этому несвязанные редакторские изменения не восстанавливают уже потраченный ассортимент рынка, нанятых бойцов или другой накопленный runtime-state.

Поддерживаются:

- **гарнизоны** города, замка, форта и руин: attached runtime-блок `14375` байт, до 12 персонажей, уровни, артефакты руин, дополнительная защита, formation, tactical strength, payment, HP sum и total cost;
- **казармы**: шесть recruit-слотов `id/current/max`, при несвязанной правке сохраняется уже уменьшившийся текущий запас; явная смена типа рекрута пересоздаёт соответствующий слот;
- **рынки**: фиксированные товары, вместимость и диапазон цен; существующий runtime-ассортимент сохраняется, а для нового рынка допустимый случайный ассортимент создаётся детерминированно по тем же ограничениям диапазона цены, поскольку оригинальный RNG между независимыми загрузками не воспроизводим;
- **церкви/святилища**: пять `spell_ids`;
- owner, group, relations, gold/mana income, hero-start flags и остальные подтверждённые V.4 поля.

Структурное удаление/вставка строений обновляет Building ID в событиях, стартовых зданиях героя/NPC и compiled-grid. Нативные карты могут иметь **перекрывающиеся footprint строений**: field `+5` в общей клетке принадлежит более поздней `BuildingData`-записи. QuestSync воспроизводит это правило вместо запрета пересечений.

После сборки выполняется строгий verifier: повторно разбирается итоговый SAV, проверяются границы/координаты runtime-core, rebuilt-garrison blocks, Building-ID ссылок событий и anchor/footprint навигация compiled-grid.


## Вкладки отчёта GUI

После анализа изменения разделены по вкладкам:

- **События** — состояние события, действие, изменённые поля и тексты;
- **Строения** — добавляемые строения, тип, координаты, изображение и runtime-блок;
- **Армии** — добавление, изменение и удаление армий, состав, координаты, тексты и бинарные изменения;
- **Фонарь/Events** — добавленные, изменённые и удалённые записи с координатами и побайтовыми отличиями;
- **Ландшафт** — координаты каждой изменённой клетки и тип `было → стало`;
- **Декор** — добавление, удаление и перемещение объектов, координаты, UGS-тип, проходимость и footprint.

Число в заголовке вкладки показывает количество строк соответствующего отчёта.

## Как переносятся фонари

Фонари можно добавлять, перемещать, удалять и полностью редактировать, включая модель,
радиус и связи с событиями. Программа переносит 99-байтовые записи, сохраняет устойчивые
ID, обновляет счётчики и заново строит клеточные ссылки фонарей.

## Как переносится ландшафт

Поддерживаются все 16 типов поверхности, одиночные клетки и группы. Программа
обновляет упакованный тип клетки, три служебных слоя проходимости и визуальный цвет.
Декорации над изменённой поверхностью накладываются заново. Клетки со строением,
фонарём или неизвестным служебным объектом блокируются для безопасности прогресса.

## Как переносятся декорации

Декорации можно добавлять в конец списка, перемещать, заменять и удалять. `Graphics\Objects\Objects.ugs`
обязательно загружается при старте из корневой папки игры и используется для определения вида объекта,
размер изображения, служебный цвет и прозрачность. Затем она:

- записывает ID объекта в подтверждённое поле клеточной таблицы;
- обновляет обе скрытые сетки проходимости/высоты по всей области объекта;
- обновляет визуальную RGB565-сетку по размеру изображения объекта;
- поддерживает карты 100×100 и 200×200 без жёстко заданных адресов.

При перемещении, замене или удалении программа восстанавливает поверхность только в
затронутых клетках и заново накладывает пересекающиеся декорации в порядке карты.
Ландшафт и список декораций можно менять одновременно, в том числе в одной и той же
области: сначала восстанавливается новая поверхность и её служебные слои, затем поверх
неё заново накладывается новый список декораций. Если там находится строение, фонарь
или другой неоднозначный служебный объект, преобразование останавливается без записи
результата.

Адреса и правила проходимости подтверждены контрольными SAV для всех десяти групп
декораций, встречающихся в игре. Смешивание служебного цвета `Objects.ugs` с цветом
поверхности пока экспериментальное: отклонение контрольных клеток не превышает трёх
единиц одного 5/6-битного канала, но результат не всегда побайтно совпадает с игрой.
Поэтому результат с новыми декорациями обязательно сначала проверяйте в игре на копии.

## Синхронизация армий

Во вкладке **«Армии»** показываются добавление, изменение и удаление армий, изменения состава и трёх текстовых полей. Поддерживается физическое добавление армии в конец списка и удаление армии из любого места списка с перенумерацией последующих ID. При этом программа обновляет известные ссылки на армии в событиях, владельцев строений и маркеры армий в клеточной таблице.

Для существующей армии синхронизируются подтверждённые runtime-поля: состав до 12 персонажей, уровни, артефакты и наложенное заклинание, активность, домашние и текущие координаты, группа и отношения, стартовое строение, патруль и его границы, агрессия, время возрождения, доход, тактическая сила, выплата и суммарные HP. При удалении персонажа оставшиеся 475-байтовые runtime-записи сдвигаются без пересоздания, поэтому их накопленное состояние сохраняется. При добавлении нового персонажа создаётся новая runtime-запись по актуальному `Rus_Units.ini`; артефакты и заклинания берутся из `Rus_Artefacts.ini` и `Rus_Spells.ini`, а `CostRecruitDiv` — из `_Global.ini`. Встроенный `army_catalog.json` используется только как проверенный эталон для сравнения.

Синхронизация консервативная: если соответствующее runtime-поле текущего SAV уже отличается от значения, ожидаемого по оригинальной DTm, это считается игровым прогрессом и не перезаписывается без необходимости. Непонятные AI/slot-поля сохраняются за текущим runtime-слотом, а не вычисляются заново. Структурное выравнивание поддерживает несколько добавлений/удалений за один проход, вставку в середину, перестановку неизменённых армий и случай «удаление + добавление при неизменном общем количестве». Header `+0x000..+0x7FF` остаётся за destination-slot, а тело `+0x800..` — за переносимой армией.

После перестройки выполняется строгий runtime-verifier: проверяются размер `0x3827`, `unit_count <= 12`, состав, границы 475-байтовых Unit-записей, aggregate strength, HP sum, formation и нулевой остаток пересобранной unit-area. Неизвестные derived-поля больше не подменяются эвристикой в обычной конвертации: если для совершенно нового юнита/сочетания артефактов/заклинания нет нативного шаблона или подтверждённого профиля, создание SAV останавливается с ошибкой. Эвристический режим оставлен только как внутренний research API.

### Нативное распределение артефактов

Контроль `Другой берег4 → Другой берег3` изменяет только четыре существующие армии (#62–#65) и добавляет по три артефакта каждой. По 12/12 предметам восстановлено правило загрузчика: `items_ids` обрабатываются слева направо; для очередного предмета перебираются все юниты, которые могут надеть его в текущем состоянии, и предмет получает юнит с максимальным немедленным приростом текущей тактической стоимости. При равенстве сохраняется порядок юнитов. Учитываются нативные ограничения экипировки: Mecha не экипируется, Magic affinity должна совпадать, `Type=Item` не надевается, у юнита может быть только одно оружие любого типа, а Armor/Shield/Helm/Ring/Amulet не дублируются.

Для существующей армии с неизменным составом изменение item/spell не перестраивает formation с нуля: overflow/reserve остаются на своих местах, а внутри основной front/back-линии пересортировываются только уже находившиеся там юниты по новой modified tactical strength. Это точно воспроизводит formation всех четырёх армий контроля. Runtime-body армий #63/#64/#65 совпадает с нативным `Другой берег3.sav` побайтно; у #62 остаётся один независимый от DTm-правки opaque model-byte `+0x81C`, который различается между отдельными нативными загрузками. Все байты, вызванные артефактной правкой, совпадают.

## Нативные Unit-профили и расширение корпуса

Каталог содержит все 102 Unit-профиля на уровне исходных INI-статов. Объединённый нативный корпус (`New.DTm/New1*.sav/New2.*` плюс `Другой берег*.DTm/SAV`) содержит все 102 Unit ID и дал 210 подтверждённых сочетаний `Unit ID + level`; уровень 0 нативно подтверждён для всех 102 Unit ID. Для них сохранены конфликт-свободные `v1/v2`, base strength и class; дополнительно сохранен 136 точных modified-профилей для реально встречавшихся сочетаний spell/artifacts.


Отдельный `New.DTm/New.sav` с 102 одиночными NPC-армиями используется как level-0 профильный контроль: strict verifier проходит 102/102 блоков, а no-op `SAV + исходная DTm -> та же DTm` возвращает побайтно тот же упакованный SAV. На полностью пустых/неактивных картах без building/lantern/army cell-marker QuestSync использует только byte-certified `MapLDV V.4` layout-профили для 100×100 и 200×200; неизвестный размер по-прежнему отклоняется вместо угадывания.
`Выплата` больше не является эмпирическим derived-полем. Она вычисляется по формуле редактора: `Round((Cost / CostGoldDiv / CostRecruitDiv) * K)` с .NET banker's rounding, `CostRecruitDiv=2` по умолчанию и коэффициентами `0.25/0.50/0.75/1.00` для диапазонов `Cost <=50 / <=100 / <=150 / >150`. Уровень на выплату не влияет.

Также перенесён расчёт `CalculateTacticalStrength/CalculateTacticCost` из IL `Editor1.3.10.1.exe`. Формула используется для проверяемого/research-расчёта derived strength; для production strict-mode нативные профили имеют приоритет, поскольку игровой runtime в отдельных Bonus-ветках отличается от редактора. В частности, нативный корпус подтверждает runtime-совместимость `GodStrike +20` и `GodAnger +10`, тогда как редактор содержит обратные прибавки.

Чтобы расширить покрытие новым нативным сохранением:

```text
python army_profile_miner.py scan native.sav original.DTm -o scan.json
python army_profile_miner.py merge scan1.json scan2.json scan3.json -o army_native_profiles.json
```

`scan` извлекает Unit ID/level, артефакты, spell, базовые `v1/v2/strength/class`, modified `v1/v2/strength`, диагностический per-Unit снимок `+0x1E9D` и точный context-keyed профиль этого dword по семантической 89-байтовой ArmyData-записи (координаты и editor Army ID исключены). Новый контроль со 102 одиночными армиями доказал, что `+0x1E9D` не является универсальным `Unit ID -> code`: после объединения корпуса 17 Unit ID имеют разные значения в разных контекстах. Поэтому production вообще не использует per-Unit fallback. Вместо него доступны 185 конфликт-свободных контекстных профилей `+0x1E9D` и 0 контекстных конфликтов. Payment не майнится: он вычисляется точной формулой из `Cost`, `CostGoldDiv` и `CostRecruitDiv`.

## Строгая схема Army-ID ссылок

Для `MapLDV V.4` централизованы все известные места, где Army ID требует структурной перенумерации: клеточный marker `(ID+1)*0x0101` при `field4=18`, owner строения `+292` и 16 байтов `EventData`: `15,16,54,55,67,68,74,75,121,122,123,136,142,144,146,147`. Event-remap реализован одной функцией, которая меняет только эти 16 байтов; regression-тест отдельно проверяет отсутствие записи в остальные 155 байтов события.

## Что приложение сохраняет без изменений

- имя и метаданные слота;
- рельеф и слои декораций вне затронутых клеток;
- runtime-прогресс существующих строений сохраняется трёхсторонним merge; гарнизон/рынок/казармы перестраиваются только при соответствующей DTm-правке;
- состояние героя;
- накопленное runtime-состояние существующих армий и юнитов, если оно не требуется для применяемой правки;
- неизвестные/нерасшифрованные AI-поля runtime-слотов армий;
- неизменённые фонари;
- уже затронутые события, кроме обязательной структурной перенумерации ссылок на удалённые/сдвинутые армии;
- остальной динамический прогресс сохранения.

При встрече `#HERONAME` приложение пытается сохранить уже подставленное в SAV имя героя.

## Ограничения

- размеры карты должны оставаться прежними;
- армия поддерживает максимум 12 runtime-персонажей;
- создание совершенно нового персонажа в production strict-mode разрешается только при наличии нативного шаблона либо подтверждённого base/modified runtime-профиля; непокрытый уровень или spell/artifact-комбинация останавливает конвертацию вместо записи непроверенной strength; выплата при этом всегда вычисляется точной формулой;
- неизвестные AI/служебные поля не вычисляются из DTm: при изменении существующих армий они сохраняются из SAV, при структурном сдвиге сохраняются за destination-slot;
- три текстовых поля армий переносятся вместе со структурными изменениями;
- простое добавление декораций выполняется только в конец списка, а их области не должны пересекаться;
- произвольное изменение порядка неизменённых декораций не поддерживается;
- перемещение/удаление рядом со строением, фонарём или неизвестным служебным объектом блокируется;
- для новых декораций нужен оригинальный `Graphics\Objects\Objects.ugs`;
- для совершенно нового рынка оригинальный runtime RNG ассортимента не может быть воспроизведён побайтно между независимыми загрузками; QuestSync создаёт детерминированный допустимый ассортимент, а у существующего рынка сохраняет фактический SAV-state;
- порядок/ID событий должен сохраняться;
- новые события можно добавлять только в конец списка и они должны относиться к будущему игровому времени;
- будущие события могут ссылаться на добавленное строение, если нужный ID уже записан в изменённой DTm;
- изменённую DTm нужно отдельно установить туда, откуда её загружает игра;
- добавление или замена пользовательских изображений событий пока не поддерживается.

Приложение запрещает перезапись исходного сохранения. По умолчанию рядом с результатом создаётся JSON-отчёт со списком перенесённых и сохранённых событий.

## Проверки

На предоставленных картах и сохранениях подтверждено:

- неизменённая DTm создаёт SAV, побайтно идентичный исходному;
- изменение одного будущего события переносится в результат;
- уже затронутые события сохраняются побайтно;
- текст может становиться длиннее или короче, динамический хвост при этом переносится без изменений;
- добавленное пустое строение получает корректную запись и служебный блок гарнизона;
- служебный блок нового строения совпадает с контрольным SAV побайтно;
- все 14 типов пустых строений дают клеточную таблицу, совпадающую с контрольным SAV;
- добавленный фонарь даёт клеточную таблицу и секцию фонарей, совпадающие с контрольным SAV;
- добавление одного и семи будущих событий даёт секцию событий, совпадающую с контрольными SAV;
- добавление новой армии №44, добавление Бомбардира в существующую армию, удаление Грабителя, удаление последней армии и удаление армии №22 из середины списка проверены по отдельным нативным контрольным SAV;
- во всех пяти армейских контрольных сценариях совпали счётчики, клеточные слои, владельцы строений, события и все строки кроме намеренно сохранённого имени исходного сценария;
- тела runtime-блоков NPC-армий (`+0x800..конец блока`) в этих контрольных сценариях совпали с нативными SAV побайтно;
- неизменённая DTm даёт полностью идентичный распакованный payload SAV;
- динамический хвост исходного прогресса при этих добавлениях остаётся неизменным;
- два скрытых слоя декораций, визуальная сетка и таблица объектов разобраны для карт 100×100 и 200×200;
- проверены все десять UGS-групп декораций и все 15 классов размеров; выжженные холмы и горы используют квадратную область по ширине спрайта;
- итоговый контейнер повторно распаковывается и проходит проверку размеров всех BZip2-блоков;
- общий автоматический набор содержит 95 unit/regression/property тестов; дополнительно выполняются 2000 seeded fuzz-проверок сохранения exact-survivors, 500 структурных fuzz-последовательностей и формальный 50-case delete/insert corpus;
- отдельно покрыты same-count delete+insert, несколько structural edits, reorder, middle insertion с destination-slot headers, лимиты 0/1/12/13 units, strict verifier corruption cases, Army-ID remap и известные artifact/spell-derived комбинации;
- объединённый нативный корпус покрывает 102/102 Unit ID, 210 точных `Unit+Level` base-профилей и 136 modified spell/artifact-профилей; 105 runtime-unit observations из `New1.sav` пересобираются в strict-mode без расхождений по stat-blocks, base/modified strength и class;
- контроль `New1.sav + New.DTm → New2.DTm` воспроизводит нативную структурную замену средней армии: compiled grid совпадает побайтно, а тела всех 15 NPC runtime-блоков `+0x800..конец` совпадают с `New2.sav` побайтно; opaque header `+0x000..+0x7FF` намеренно сохраняется за destination-slot;
- контроль `Другой берег4.sav + Другой берег4.DTm → Другой берег3.DTm` подтверждает native greedy-раздачу 12/12 артефактов между юнитами четырёх существующих армий и lane-local formation resort; runtime-body армий #63/#64/#65 совпадают побайтно, а в #62 все байты, вызванные DTm-правкой, совпадают (единственный независимый opaque model-byte `+0x81C` намеренно сохраняется из исходного SAV);
- контроль `Другой берег.sav + Другой берег.DTm → Другой берег2.DTm` подтверждает создание новой армии #62 из 12 юнитов: formation строится по modified strength и доминирующему типу атаки с переносом переполненной линии; все 62/62 NPC runtime-body `+0x800..конец`, включая новую 12-юнитную армию, совпадают с нативным `Другой берег2.sav` побайтно; companion patrol mode `+0x1F10` подтверждён 62/62 (`8` только для patrol radius 0, иначе `5`). - locator SAV дополнительно проверен на картах без buildings/events и при отличающемся scenario title: dynamic tail и cell table находятся структурно, в том числе для полностью пустой 100×100 карты.
